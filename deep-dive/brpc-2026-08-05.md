> 生成日期: 2026-08-05

## 1. 概述 -- bRPC 在项目里扮演什么角色

bRPC (better RPC) 是 Apache 开源的一个 C++ RPC 框架，百度大规模生产环境打磨出来。在 NovaChat 中，它是**整个 C++ 服务层的核心骨架** -- 所有网络 I/O、RPC 调用、协议转换都由它承担。

**bRPC 在项目中的四个角色**：

```
角色 1: RPC Server      user-service (:8001) + message-service (:8002)
                        接收 HTTP+JSON 请求 -> 自动转 Protobuf -> 分发到正确方法

角色 2: HTTP Client     PushDispatcher -> 向网关 PushService 发 HTTP POST
                        (brpc::Channel + PROTOCOL_HTTP)

角色 3: Redis Client    C++ 代码读写 Redis，不引入 hiredis
                        (brpc::Channel + PROTOCOL_REDIS + 手动 RESP 解析)

角色 4: Service Stub    手写的 bRPC Service 基类
                        (DescriptorPool + CallMethod 分发 12/4 个 RPC)
```

## 2. 核心概念一：http+pb -- 项目最大的技术亮点

**这是面试中最应该讲清楚的东西。**

gRPC 要求统一用 Protobuf 二进制协议，如果 TS 要调 C++，需要 grpc-web + envoy proxy 做协议转换。bRPC 的 `http+pb` 协议直接支持 HTTP JSON 到 Protobuf 自动转换。

### TS 端 (gateway/src/clients/base.ts:52-124)

```typescript
// 零依赖！不需要 import 任何 protobuf 库，不需要 grpc-web
class BrpcClient {
  async call(serviceName, methodName, body, opts) {
    // 端点格式: http://user-service:8001/nova.user.UserService/Register
    const url = `${this.baseUrl}/${serviceName}/${methodName}`;
    const response = await fetch(url, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(body),
      signal: AbortSignal.timeout(opts.timeout ?? 5000),
    });
    return response.json();
  }
}
```

### C++ 端 (services/user-service/server.cc:135-179)

```cpp
// 1. 注册服务 -- bRPC 从此知道这个 service 有哪些方法
server.AddService(&service_impl, brpc::SERVER_DOESNT_OWN_SERVICE);

// 2. 启动 -- 监听 HTTP 端口
butil::EndPoint ep;
butil::str2endpoint("0.0.0.0", 8001, &ep);
server.Start(ep, &options);

// 3. bRPC 自动完成的事：
//    (a) 解析 URL -> service="nova.user.UserService", method="Register"
//    (b) Content-Type=application/json -> 触发 json2pb 转换
//    (c) JSON body -> RegisterReq {username, password} (强类型!)
//    (d) 调用 UserServiceImpl::Register(controller, &req, &resp, done)
//    (e) 返回时 protobuf -> json -> HTTP 200

// 4. 优雅关闭
server.RunUntilAskedToQuit();  // 阻塞直到 SIGINT/SIGTERM
server.Stop(5000);               // 排空连接，最多等 5 秒
```

### 整个转换链路

```
TS: fetch("url", {body: JSON})
        |
        | HTTP POST (JSON body)
        v
bRPC Server 收到请求:
  1) parse URL: /nova.user.UserService/Register
     -> service = "nova.user.UserService"
     -> method  = "Register"
  2) 查 ServiceDescriptor -> 找到 MethodDescriptor("Register")
  3) 查 MethodDescriptor -> 找到 input_type = RegisterReq
  4) json2pb(JSON_body, RegisterReq*)      <-- 自动转换!
        |
        v
C++ 代码拿到强类型对象:
  const RegisterReq* req;
  req->username()  // "alice"
  req->password()  // "***"
        |
        | 业务逻辑处理
        v
C++ 返回:
  RegisterResp resp;
  resp.set_user_id(333855473985916928);
  done->Run();
        |
        v
bRPC 自动:
  5) pb2json(RegisterResp) -> JSON string
  6) HTTP 200 Response
        |
        v
TS: response.json() -> { user_id: ..., access_token: "..." }
```

**关键理解**：TS 网关从头到尾不知道 Protobuf 的存在。它只发 JSON、收 JSON。强类型校验、序列化、反序列化全在 C++ 侧由 bRPC 完成。

## 3. 核心概念二：手写 bRPC Service Stub

### 为什么要手写？

protoc-gen-brpc (bRPC 的 proto 代码生成插件) 需要 bRPC 源码编译，Docker 环境构建不稳定。而且 bRPC 1.11.0 的 protoc plugin API 有变化。所以手写了约 200 行的 bRPC service stub。

### 手写了什么

**基类** (user.brpc.h:17-120) -- 12 个纯虚函数 + 4 个 Service 接口:

```cpp
class UserServiceBase : public ::google::protobuf::Service {
public:
    // 12 个 RPC 方法 -- 纯虚，子类实现业务逻辑
    virtual void Register(RpcController*, const RegisterReq*,
                          RegisterResp*, Closure* done) = 0;
    virtual void Login(RpcController*, const LoginReq*,
                       LoginResp*, Closure* done) = 0;
    // ... 10 more ...

    // 4 个必须实现的 Service 接口:
    const ServiceDescriptor* GetDescriptor() override;
    void CallMethod(...) override;              // 按名字分发到具体方法
    const Message& GetRequestPrototype(...) const override;
    const Message& GetResponsePrototype(...) const override;
};
```

**分发器** (user.brpc.cc:24-86) -- CallMethod 的 if-else 链:

```cpp
void UserServiceBase::CallMethod(
    const MethodDescriptor* method,  // bRPC 告诉你调用哪个方法
    RpcController* controller,
    const Message* request,          // json2pb 已转换好的请求
    Message* response,
    Closure* done)
{
    const string& name = method->name();

    if (name == "Register") {
        Register(controller,
                 static_cast<const RegisterReq*>(request),  // 向下转型
                 static_cast<RegisterResp*>(response), done);
    } else if (name == "Login") {
        Login(controller, ...);
    }
    // ... 10 more if-else branches
}
```

### bRPC 内部的调用流程 (6 步)

```
1. bRPC 收到 HTTP POST /nova.user.UserService/Register
2. 查 ServiceDescriptor -> 找到 MethodDescriptor("Register")
3. 调用 GetRequestPrototype("Register") -> 创建空的 RegisterReq 对象
4. json2pb(HTTP_body, 空RegisterReq) -> 填充字段
5. 调用 CallMethod(method_desc, controller, &filled_req, &empty_resp, done)
6. CallMethod 内部 if-else 链 -> 调用 Register() 虚函数 (我们的业务代码)
```

**面试要点**："因为 protoc-gen-brpc 不可用，我手写了 dynamic DescriptorPool 构建和 CallMethod 分发。这让我深入理解了 bRPC 的 service descriptor 机制。"

## 4. 核心概念三：brpc::Channel 统一 I/O 模型

这是项目最底层的设计决策：**C++ 代码中所有网络 I/O 全部通过 brpc::Channel**。

### 4.1 作为 HTTP Client (push_dispatcher.cc:55-99)

消息服务反向推送消息到网关时:

```cpp
bool PushDispatcher::CallGatewayPush(const PushUpdateReq& req) {
    // 1. Protobuf -> JSON 序列化
    string json_body;
    google::protobuf::util::MessageToJsonString(req, &json_body);

    // 2. 创建 HTTP Channel
    brpc::Channel channel;
    brpc::ChannelOptions options;
    options.protocol = brpc::PROTOCOL_HTTP;
    options.timeout_ms = 3000;
    options.max_retry = 1;
    channel.Init("gateway:3000", &options);

    // 3. 构造 HTTP 请求
    brpc::Controller cntl;
    cntl.http_request().uri() = "/nova.gateway.PushService/PushUpdate";
    cntl.http_request().set_method(brpc::HTTP_METHOD_POST);
    cntl.http_request().SetHeader("Content-Type", "application/json");
    cntl.request_attachment().append(json_body);

    // 4. 发送 (同步写法，bthread 自动挂起不阻塞 pthread)
    channel.CallMethod(nullptr, &cntl, nullptr, nullptr, nullptr);

    // 5. 结果检查
    if (cntl.Failed()) {
        // 推送失败 -> 消息已存，用户上线后 GetMessages 拉取，不丢
        return false;
    }
    return true;
}
```

### 4.2 作为 Redis Client (redis_client.cpp:65-97, 191-204)

**为什么不用 hiredis？** hiredis 有自己的事件循环 (epoll)，和 bRPC 的 bthread 是两个独立的 I/O 模型，混用会导致：
- 两个调度器互相不知道对方在阻塞
- 线程模型复杂，难以调试
- 无法享受 bthread 的协程调度

解决方法 -- 用 bRPC 的 `PROTOCOL_REDIS` 模式:

```cpp
bool RedisClient::Init(const string& addr, int port, const string& password) {
    brpc::ChannelOptions options;
    options.protocol = brpc::PROTOCOL_REDIS;           // bRPC 内置 Redis 协议!
    options.connection_type = brpc::CONNECTION_TYPE_POOLED;
    channel_.Init("redis:6379", &options);
    // ...
}

butil::Status RedisClient::Set(const string& key, const string& value,
                                int ttl_sec) {
    // 手动构建 RESP 协议命令:
    // SET mykey myvalue EX 300
    // -> *5\r\n$3\r\nSET\r\n$5\r\nmykey\r\n$7\r\nmyvalue\r\n
    //    $2\r\nEX\r\n$3\r\n300\r\n
    string cmd = RespCommand({"SET", key, value, "EX", to_string(ttl_sec)});

    brpc::Controller cntl;
    cntl.request_attachment().append(cmd);  // 命令放 attachment
    channel_.CallMethod(nullptr, &cntl, nullptr, nullptr, nullptr);
    // bthread 在这里挂起，Redis 回复到达后自动唤醒

    string reply = cntl.response_attachment().to_string();
    // 解析 RESP 响应: +OK / -ERR / :123 / $5\r\nhello\r\n / $-1\r\n
    return IsRespOk(reply) ? Status::OK() : Status(-1, "SET failed");
}
```

**RESP 协议简表** (185 行手写解析器在 redis_client.cpp:99-157):

```
+OK\r\n          -> 简单字符串, 成功
-ERR msg\r\n     -> 错误响应
:123\r\n         -> 整数
$5\r\nhello\r\n  -> 批量字符串 (5 bytes: "hello")
$-1\r\n          -> null (key 不存在)
*N\r\n...        -> 数组 (HGETALL / SMEMBERS 返回)
```

**同样的模式也用在 MySQL** -- brpc::Channel + PROTOCOL_MYSQL，解析 MySQL 文本协议响应 (列计数 -> 列定义 -> 数据行 -> EOF)。

### 统一 I/O 的价值

```
传统做法 (三套 I/O 模型):
  Redis  -> hiredis (自己的 epoll 线程)
  MySQL  -> libmysqlclient (阻塞 I/O)
  RPC    -> bRPC (bthread 协程)
  结果: 三种调度模型混在一起, 难以定位性能瓶颈

NovaChat 做法 (统一):
  Redis  -> brpc::Channel + PROTOCOL_REDIS
  MySQL  -> brpc::Channel + PROTOCOL_MYSQL
  RPC    -> brpc::Server + http+pb
  结果: 全部走 bthread 调度, 一套事件循环, 同步代码异步执行
```

## 5. 核心概念四：bthread -- M:N 协程

bRPC 的并发模型是 bthread (baidu thread)，一种 M:N 用户态协程:

```
传统 pthread (1:1):
  1000 个并发请求 = 1000 个 pthread
  上下文切换 ~1us (内核态)
  每个线程栈 8MB -> 8GB 内存
  线程数受系统限制 (一般 < 10000)

bthread (M:N):
  1000 个并发请求 = 1000 个 bthread
  跑在 8 个 pthread (bthread_worker) 上
  上下文切换 ~10ns (用户态)
  每个 bthread 栈 1MB -> 1GB 内存 (分摊)
  可以创建数十万个 bthread
```

**在 NovaChat 中的应用：你写同步代码，bRPC 自动帮你异步化:**

```cpp
// user_service_impl.cc:Register()
// 这段代码 "看起来" 是同步的:
auto user_id = snowflake_->NextId();              // 本地生成，立即返回
auto hash = nova::HashPassword(password);          // CPU 计算，立即返回
user_dao_->CreateUser(record);                     // 可能走 MySQL -> bthread 挂起
                                                   // MySQL 回复 -> bthread 唤醒
// 继续执行：签发 token、填充 response...
// 整个过程用同步写法，但 I/O 期间不浪费 pthread
```

**对 NovaChat 的意义：**

- user-service 的 12 个 RPC 全是同步代码风格
- 底层 MySQL/Redis I/O 不会阻塞整个服务
- 4 核机器就能处理几万并发 QPS

## 6. 面试追问速答

### Q: bRPC 和 gRPC 的核心区别？

| 维度 | bRPC | gRPC |
|------|------|------|
| 协议 | http+pb (JSON 自动转 Protobuf) | HTTP/2 + Protobuf binary only |
| TS 调 C++ | fetch() 即可 | 需要 grpc-web + envoy proxy |
| 协程 | bthread M:N | 线程池/回调/协程 (语言相关) |
| 服务治理 | 内置 /status /vars 监控 | 需要外部收集 (Prometheus) |
| 生态 | 中文社区, 百度生产验证 | 英文社区, Google 生产验证 |

**选 bRPC 的核心原因**：http+pb 让 TS 网关和 C++ 服务之间的通信零适配层，这在异构语言微服务中是决定性的便利。

### Q: bthread 和 Go goroutine 的异同？

- **相同**：都是 M:N 协程，同步写异步跑，用户态切换快
- **不同**：
  - bthread 基于 C++ 实现 (makecontext/swapcontext 或汇编)
  - goroutine 是 Go runtime 原生支持，栈可以动态增长 (起始 2KB)
  - bthread 栈固定 1MB
  - bthread 主要服务于 RPC 的 I/O 密集场景

### Q: 为什么 SERVER_DOESNT_OWN_SERVICE？

```cpp
server.AddService(&service_impl, brpc::SERVER_DOESNT_OWN_SERVICE);
```

`service_impl` 是栈上对象，生命周期由 main() 管理。如果传 `SERVER_OWNS_SERVICE`，bRPC 会在 Server 析构时 delete 它 -- 这会 crash (栈上对象不能 delete)。`SERVER_DOESNT_OWN_SERVICE` 告诉 bRPC：不要管这个对象的内存。

### Q: 为什么 C++ Redis 要手写 RESP 解析？

bRPC 的 `PROTOCOL_REDIS` 只管网络层 (连接、请求/响应匹配)，存粹把协议数据当 attachment 传。Redis 命令和回复的序列化/反序列化由应用层自己处理。所以手写了：
- 编码器 `RespCommand()` (构建 `*N\r\n$len\r\ndata\r\n` 格式)
- 解析器 `ParseBulkStringContent()` (读取 `$len\r\ndata\r\n`)
- 错误检测 `IsRespOk()` / `IsRespError()`

### Q: 为什么不直接用 gRPC + grpc-web？

- grpc-web 需要在 TS 和 C++ 之间加一个 envoy proxy 做协议转换
- 多了 1 个组件 = 多了 1 个故障点 + 1 个运维对象
- bRPC 在 C++ 侧原生支持 http+pb，不需要中间层
- 对 NovaChat 这种小型分布式系统来说，减少组件就是减少复杂度
