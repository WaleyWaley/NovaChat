## 四、最容易被追问穿的 6 个点

1. **“不丢？DB 写成功、推送前宕机呢？”**  
   答：消息已经落库就算可靠；用户上线用 Timeline 拉，客户端重试带同一个 idempotency_key，服务端返回已存在，不会重复。

2. **“不重？网关转发重试呢？”**  
   答：C++ 侧 push_id 用雪花生成，网关用本地 Set 去重；跨网关转发透传同一个 push_id，目标网关再去重一次。

3. **“不乱序？多端登录、群聊呢？”**  
   答：只承诺单会话有序；多端要靠客户端按 msg_id 重排；群聊要么单写者生成序列号，要么按群维度做会话级序列，不能吹全局有序。

4. **“Redis 单点、MySQL 单点，还叫高可用？”**  
   答：当前是开发单机版；生产要 Redis Sentinel/Cluster、MySQL 主从，路由表 TTL 过期要能重建。降级时本机可服务，跨网关转发关闭，靠离线拉取兜底。

5. **“压测数字不高，凭什么说并发承载力优秀？”**  
   答：这是同机 Docker、限流放开的基线，瓶颈已经定位到 PBKDF2 和 8 连接池；不是架构上限。给我更大池子和独立压测机，能给出线性提升的数据。

6. **“三级存储是不是包装？”**  
   答：不要硬说 UserService 内部三级缓存。标准说法是：**用户服务以 MySQL 为底账、内存做降级；Redis 属于网关侧在线路由/共享状态，系统整体是三层存储。** 这样既贴合代码，也不会被追问缓存命中率。

## 五、项目追问补充

### 5.1 网关如何用 HTTP + JSON 调用 C++ bRPC

**30 秒版：**  
bRPC 服务端启用了 http+pb 协议。网关不需要 Protobuf 库，只按 `/{package.Service}/{Method}` 拼 URL，发标准 HTTP POST，Body 是 JSON，`Content-Type: application/json`。bRPC 收到后按 URL 找到 service 和 method，再根据 MethodDescriptor 拿到请求类型，把 JSON 自动反序列化成 Protobuf 对象，调用 C++ 实现；实现填好 response，`done->Run()` 后 bRPC 再按请求的 Content-Type 把 Protobuf 转回 JSON。网关拿到 JSON 后做 int64 精度保护和错误码映射。

**网关侧做四件事：**

1. 服务注册表记录服务地址和完整 Protobuf 服务名。
2. 统一客户端拼 URL、发 POST、序列化 JSON。
3. 超时控制：默认 5 秒，超时映射 408，网络错误映射 503。
4. 鉴权后注入 user_id；响应先读原始文本，再处理大整数，最后检查业务 `error_code`。

**bRPC 侧做四件事：**

1. 解析 URL，拆出 package、service、method。
2. 在已注册服务表里找到实现类和方法描述符。
3. 根据 MethodDescriptor 拿到请求消息类型，JSON → Protobuf。
4. 调用业务实现，响应 Protobuf → JSON，返回 HTTP 200。

**面试官追问：**

- **bRPC 怎么知道 JSON 转成哪个类？**  
  靠 URL 找到 MethodDescriptor，再通过 `input_type()` 拿到请求消息类型，创建空对象后做 JSON 反序列化。
- **HTTP 200 就代表成功吗？**  
  不代表。HTTP 200 只说明传输成功，业务成功要看响应里的 `error_code`。
- **为什么不用 gRPC？**  
  gRPC 的 TS 侧要引入 Protobuf 工具链和生成代码；bRPC 的 http+pb 正好满足“前端写 JSON、后端用结构体”，内部 C++ 调用还能切二进制协议。
- **服务地址写死吗？**  
  当前是配置注册表，生产应该接 Consul/Etcd 做服务发现和负载均衡，这部分是演进方向，不要说成已经实现。

### 5.2 跨语言字段和 int64 精度怎么解决

**30 秒版：**  
核心是拿 proto 当唯一契约。网关按 `/包.服务/方法` 发 HTTP POST，Body 用 JSON；bRPC 服务端用 http+pb 自动把 JSON 转成 Protobuf 对象，响应再转回 JSON。字段名按 Protobuf 的 JSON 映射处理，int64 统一按字符串传，网关解析前再保护 16 位以上整数。TS 侧只写接口类型，不引 Protobuf 工具链。

**具体做法：**

- **契约统一**：请求/响应类型、字段名、字段编号、服务名和方法名都来自 proto；字段编号不复用，保证向后兼容。
- **字段命名**：proto 用 snake_case，Protobuf 的 JSON 映射可能是 camelCase；网关对反向推送的顶层字段做归一化，透传 payload 不做深度转换。
- **默认值**：proto3 没传的字符串是空串、数字是 0、布尔是 false，不能把“没传”当成“一定有值”。
- **枚举**：JSON 里可能是枚举名，也可能是数字，统一按协议约定处理。
- **bytes**：JSON 里按 base64 传。
- **int64 精度**：Protobuf 的 int64 在 JSON 里默认序列化成字符串；TS 类型用 `string | number`；网关解析前把 16 位以上整数字面量加引号，再 `JSON.parse`，避免雪花 ID 被舍入。
- **错误码**：所有 C++ 服务统一返回 `error_code + error_message`，TS 和 C++ 对“成功”的定义一致。

**当前不足：**  
TS 侧类型是手写对齐 proto 的，没有代码生成。更严谨的做法是用 ts-proto / protobuf-es 从同一份 proto 生成 TS 类型，消除契约漂移风险。

### 5.3 消息如何保证不丢不重

**30 秒版：**  
原则是实时推送只负责加速，MySQL 落库才是真相。发送时先落库再返回成功，推送失败或离线都靠上线 Timeline 拉取；客户端崩溃没收到，也靠重连同步补齐。不重靠三层：客户端 idempotency_key + DB 唯一索引挡住重复发送，push_id 挡住推送重试，客户端再按 msg_id 幂等。严格说是至少一次投递，客户端去重。

**不丢：五层兜底**

1. 先落库，再返回成功；写失败就返回错误，不假装成功。
2. 推送失败不算丢消息，消息已经在库里。
3. 离线用户上线后通过 GetConversation / GetMessages 拉取，会话列表用 GetDialogs 恢复，未读和最后已读用 GetSyncState 恢复。
4. 客户端崩溃、没收到推送，就不会更新本地游标，下次重连重新拉取。
5. DB 成功但响应丢了，客户端重试带同一个 idempotency_key，唯一索引挡住第二次插入。

**不重：三层**

1. 发送侧：客户端生成 idempotency_key，DB 唯一索引兜底；重复插入返回 1062，服务端返回成功但 `is_new=false`。
2. 推送侧：C++ 生成 push_id，网关本地 Set 去重；跨网关透传同一个 push_id，目标网关再去重一次。
3. 客户端侧：按 msg_id 幂等，同一条消息只渲染一次。

**“推送成功但客户端没收到”怎么解释**

- 网关 `ws.send()` 成功只代表写进 socket 缓冲区，不代表客户端应用真的收到。
- 当前没有逐条消息的应用层 ACK，服务端不能精确知道客户端是否收到。
- 系统不依赖推送成功来保证可靠性：消息在 MySQL，客户端没收到就不更新游标，重连后拉取，按 msg_id 去重。
- 准确说法：**服务端保证消息不丢，投递语义是至少一次；实时推送是优化，拉取是兜底。**

**边界和改进**

- ACK 目前主要用于已送达/已读状态和未读数，不是逐条可靠投递的确认；未 ACK 的消息不会自动无限重推。
- 重复请求目前返回 `is_new=false`，但没有把原消息一并返回，客户端需要通过拉取补齐；更严谨的做法是查询原消息返回。
- idempotency_key 当前是全局唯一，更严谨是按“发送者 + key”做联合唯一，避免不同用户碰撞。
- 当前推送在 SendMessage 内同步调用，推送慢会拉长发送响应；更合理是异步队列/线程池解耦。

### 5.4 Session 是干什么的

**30 秒版：**  
我的 session 是网关侧的登录会话记录，不是 WebSocket 连接。JWT 本身无状态，签出去在过期前服务端撤不回，所以我给每个 token 对生成一个 session_id 写进 JWT，网关维护 `sessionId → 用户/设备/过期时间/是否失效` 的记录。登出或改密码时把 session 标记失效，后续验 token 时除了验签和过期，还会查 session 是否被撤销，实现服务端强制下线。另外每条 WS 连接还有一个 ClientSession，只保存这条连接的用户和认证状态，两者不是一回事。

**两个 session 要分清：**

| 名称 | 作用 | 生命周期 |
|---|---|---|
| auth Session | 登录会话记录，负责撤销、设备、活跃时间 | 登录创建，登出/改密码/过期失效 |
| ClientSession | 单条 WebSocket 连接的状态封装 | 连接建立创建，连接断开销毁 |

**auth Session 的作用：**

- 解决 JWT 无法主动撤销的问题。
- 登出时标记当前 session 失效。
- 改密码、删账号时清空该用户所有 session，强制重新登录。
- 记录设备、创建时间、最后活跃时间，为多端管理和审计做基础。
- 定时清理过期和失效 session，防止内存无限增长。

**ClientSession 保存什么：**

- 这条连接对应的 WebSocket 对象。
- 是否已认证、当前 userId、username、sessionId。
- token 过期定时器，到期前主动断开 WS，逼客户端 refresh 后重连。

**和相邻概念的区别：**

| 概念 | 回答的问题 | 存在哪 |
|---|---|---|
| JWT | 你是谁、有没有过期 | 客户端持有，网关验签 |
| auth Session | 这个登录还允不允许用 | 网关侧 SessionStore |
| ClientSession | 这条 WS 连接是谁 | 每条连接一个对象 |
| ConnectionManager | 这个用户当前连在哪个 socket | 网关本地 Map |
| Redis 在线路由 | 这个用户连在哪台网关 | Redis |
| 会话/对话 | 他和谁聊天、消息到哪 | MySQL 消息表 |

**完整生命周期：**

1. 注册/登录成功，网关签发 token，生成 session_id。
2. 客户端连 WS，发 auth 消息带 access_token。
3. 网关验签、验过期、查 session 失效。
4. 认证通过后创建/更新 auth session，绑定 ClientSession，注册 ConnectionManager，写 Redis 在线路由。
5. 登出：当前 session 标记失效，并清掉该用户所有 session。
6. 改密码：该用户所有 session 标记失效，强制重新登录。
7. 定时任务清理过期和失效 session。

**当前局限：**

- SessionStore 是网关进程内内存，不是 Redis；重启会丢，多网关不共享。
- 查不到 session 时当前是放行的，不是 fail-closed；多网关或重启后旧 token 可能仍能用。
- 登出/改密码只标记失效，不会立刻踢掉已有 WS 连接，通常要等 token 过期或下次重连。
- 设备信息记录了，但还没有“最多几台设备在线”的完整多端策略。

### 5.5 JWT 鉴权

**30 秒版：**  
JWT 由网关签发：注册登录时 user-service 只验账号密码，网关生成 access 和 refresh。access 里放 user_id、username、session_id、iat、exp，默认 24 小时；refresh 里放 user_id、type=refresh、session_id，默认 30 天。header 带 kid 和算法，开发用 HS256，生产预留 RS256 公私钥分离。服务端不存 JWT，只在 SessionStore 存 session_id 对应用户、设备和失效状态；客户端存 localStorage，HTTP 用 Bearer，WebSocket 首条消息带 access_token。

**四级路由鉴权（一句话版）：**  
不是多级 token，而是按路由分四级策略：免认证（注册/登录/health/WS 握手/内部 PushService）、refresh 专用（刷新接口只认 body 里的 refresh token）、可选认证（如查用户名，没 token 也能用）、强制认证（其他接口必须带 Bearer access token，验签+过期+session 撤销）。WS 是握手免认证、首条消息再认证；PushService 是内部接口，不走用户 JWT。

**JWT 里放什么：**

| 部分 | 内容 |
|---|---|
| access payload | user_id、username、session_id、iat、exp |
| refresh payload | user_id、type=refresh、session_id、iat、exp |
| header | alg、kid |
| 不放 | 密码、手机号等敏感信息；JWT 是签名不是加密，内容可被解码 |

**哪里签发：**

- 网关的 `signToken` 签发，入口是注册、登录、刷新三个接口。
- user-service 保持无状态，只校验账号密码，不签发 token、不管理会话。
- 当前开发环境实际走 HS256 回退；代码预留 RS256 + kid 密钥轮转，生产设计是 user-service 私钥签、网关公钥验。

**存在哪里：**

- 客户端：access/refresh 存 localStorage，同时放内存；HTTP 放 `Authorization: Bearer`，WebSocket 首条 auth 消息带 access_token。
- 服务端：不存 JWT 本身，只存 session 元数据，包括 sessionId、userId、设备、过期时间、是否失效。
- 注意：当前 SessionStore 是网关进程内内存，不是 Redis；Redis 目前主要是在线路由。不要说成“session 已经放 Redis”。

**怎么验：**

1. 从 JWT header 取 kid，到 KeyStore 找对应密钥。
2. 验签名、验过期时间。
3. 再查 session 是否被标记失效，登出或改密码后会失效。
4. HTTP 由鉴权中间件做，WebSocket 由首条 auth 消息做。
5. C++ 服务信任网关注入的 user_id，不重复验 JWT。

**容易被追问的点：**

- 刷新时目前是重新签发一对 token、sessionId 不变，但没有做旧 refresh token 的一次性消费/黑名单，不要把它说成严格的 refresh token 轮转。
- 当前 session 在单网关内存里，多网关要迁 Redis，否则在一个网关登出，另一个网关不一定知道。
- access token 短有效期、refresh token 长有效期，是为了兼顾安全性和用户体验；短 token 泄露的窗口更小，refresh 用于续期。
- JWT 只适合放身份标识和会话标识，不适合放权限大对象或敏感数据；权限可以在网关或业务层再查。

### 5.6 限流

**一句话版：**  
网关层双维度令牌桶：先按 IP、再按 userId，各消费一个令牌，两个都通过才放行；没令牌返回 429 / `FLOOD_WAIT`。桶存在网关内存，按固定速率恢复，定时清理空闲桶；白名单是 health 和内部 PushService。当前是单机版，多网关要迁 Redis + Lua；WS 消息的逐条限流还没做。

### 1. 对象池 + 生产者消费者

MySQL 连接池不是每次请求都新建连接，而是启动时建 N 条连接和 N 个 worker。bthread 把 SQL 任务放进队列，worker 从队列取任务、独占一条连接执行、执行完归还并唤醒 bthread。

这解决两个问题：连接复用，避免频繁握手；把阻塞的 MySQL 调用从 bthread 卸载到 pthread，防止慢 SQL 占住 RPC 调度线程。

### 2. 门面 + 适配器

网关对客户端是一个门面：客户端只发 WebSocket JSON，不需要知道后面的 C++ 服务、bRPC、Protobuf。网关里面的 BrpcClient 又是适配器：把普通的 HTTP+JSON 调用适配成 bRPC 的 http+pb 调用。

好处是协议边界清晰。以后把 C++ 换成别的实现，或者把 HTTP 换成二进制，客户端和业务层不用改。

### 3. 观察者 / 发布订阅

消息服务落库后发布一个 Update，网关收到后推给用户的 WebSocket。发送方和接收方不直接耦合，消息服务不需要知道用户连在哪台网关，网关也不需要知道消息怎么存。

但要说清楚：当前是直接 HTTP 推送，不是 Kafka 那种持久化消息队列；离线可靠性靠 MySQL 和 Timeline 拉取兜底，不靠推送。
